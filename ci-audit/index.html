    CI/CD audit

    Audit date: 2026-11-10. Evidence combines repository source, isolated contracts, GitHub PR metadata and Actions job/step results. Local environment: macOS ARM64, Python 3.15.2, Bash 3.2. This is not certification of a live deployment.

    Workflow inventory

    Scope optimization

    The shared scripts/py/ci-scope.py resolver drives CI, PR scans and release scans. Image scopes follow Dockerfile COPY inputs, owned Dockerfiles and ignore files, plus consumed repository/ref values. Root .dockerignore affects only the two root-context web images. There are no local cross-image COPY dependencies. Tests are not image build inputs. A contract checks that current COPY sources remain covered; new Dockerfile inputs must update the resolver and contract.

    CI starts nine independent validation-group jobs and retains validate as the required aggregate. Each group runs only for its declared dependencies. Image smoke builds have independent image gates. The ten PR scan jobs and four release jobs retain their names and success aggregation; starting a job is not building or scanning an image. CI runs on every PR and main push so required checks do not remain pending and publishing can recover interrupted releases without new image inputs. MkDocs retains its docs/config/workflow path filters.

    Release comparisons deliberately differ from the event matrix: each image is compared to the source annotation on its published stable OCI index. A skipped event does not discard an earlier unpublished image change. Missing history, invalid revisions, Git errors or malformed dependency declarations conservatively enable checks/builds/scans, never report uncertainty as unchanged. NUL-delimited Git paths preserve newline filenames; disabling rename detection includes both ends of renames and deleted inputs. Pins are parsed as data, never executed.

    Script-only runtime tests load unchanged partner images from stable by immutable digest. The source must be an ancestor of HEAD and its image inputs must still match. Missing or incompatible published fixtures fail validation explicitly; there is no implicit rebuild or fallback to an unverified mutable image. Override tests rebuild only changed components; script-only override tests inject isolated payloads before startup without building. Build fixtures copy tracked files only, not ignored local overrides. Main promotion, exact-digest two-architecture security gates, approval journaling and rebuild-free recovery remain unchanged.

    check-ci-scope.py exercises synthetic commits for isolated image inputs, both pin fields, comments, script dependencies, multiple changes, renames, deletions, newline filenames and error fallbacks. Mocked fixture-loader checks cover the no-build path and metadata rejection. Local contracts cannot prove registry availability, runner execution or repository branch-protection configuration; maintainers must verify the existing validate and PR image security required checks on GitHub before merging.

Durable approval journal recovers interrupted releases without adoption-only rebuilds; changed inputs and unreliable revision still require builds and both security scans.
    P1 locally fixed publish.yml, scripts/py/publish-images.py Per-source branches and partial ready records allowed overlapping proposals; interruption lost published components and retries failed.     P2 fixed security.yml, wsproxy paths Root .dockerignore was treated as wsproxy input despite image-local build context. Remove that path from wsproxy release scope. PR/release path and context contracts pass; web root contexts retain it.

    P2 open Compose/Kubernetes MariaDB image declarations MariaDB runtime tags are outside the Dockerfile directories configured for Dependabot. Generic dependency-file edits still trigger both root-context image scans even when only a different fork pin changes.     Why scripts changes start jobs

    CI has no top-level path filter. Ten scan jobs starting is not ten images being built: their scope steps can skip every build and Trivy step. validate requires the aggregate security result and all validation-group results. Main release jobs compare published inputs before deciding whether candidates are needed. Script and deployment changes run applicable contracts or tests, not image builds. Missing comparison history conservatively enables required work.

    Deployment and security boundaries

    Root-context web images copy explicit owned inputs, not the entire repository. The root ignore rules exclude private client files, credentials and generated artifacts. Game/proxy images use owned contexts. Base image digests are pinned; npm uses lockfiles. Mutable OS repositories still affect reproducibility and require fresh security scans. PR scans include Hercules; release scans do not.

    Compose preserves existing ports and environment names; database is backend-only and client resources are read-only. Runtime stable defaults and published host ports are intentional deployment behavior, not local-test isolation guarantees. Kubernetes web pods drop capabilities, disallow privilege escalation, use non-root UID 1000 and RuntimeDefault seccomp. The database ingress policy admits only the named clients and operator; it is not a namespace-wide default-deny egress policy. Flux overlays select reviewed source tags and preserve resource identities/pruning. No live changes were made.

    Setup source inspection found explicit storage/installer prerequisites, checksum verification, refusal of existing data and interrupted setup, plus existing-node no-change checks. Flux bootstrap requires confirmation; existing installations are checked first. Offline fixtures cannot prove hardware mount behavior, Longhorn readiness, real token permissions or a successful fresh installation.

    Verification limits

    Final pre-commit source and trigger check

    Only workflow_call is enabled in publish/security. The sole repository caller is CI; its actual events are PR and main push. Security requires a main push and successful validation, and publish additionally requires successful security. PRs cannot reach promotion; dispatch, schedule and workflow_run are not enabled. Relative workflow calls resolve at the caller commit, and workflow_call inherits the caller SHA/context. Thus executable github.sha, validated checkout, candidate revision, ready-record SHA and publisher source refer to the same main-push commit, even when main advances while the run waits.

    Scans address the exact candidate digest on both architectures before ready artifacts are uploaded. Download-artifact uses this same run (no cross-run ID). Publisher rejects mismatched source/run/attempt and candidate digest/revision before journal writes or promotion; registry tags are created from approved digests and verified. Recovery retains its journal/historical proof and ancestry checks. No permissions or workflow triggers were changed in this final check.

    For workflow_run, github.sha would instead be the default-branch commit and github.event.workflow_run.head_sha the triggering revision. Supporting it would require trusted event/repository/branch/conclusion validation plus explicit source, run/attempt and artifact binding; substituting head_sha alone is insufficient. The new regression uses different default-branch and approved SHAs: the wrong source fails without registry/GitOps mutation, the approved source succeeds. Trigger/gate contracts prohibit accidentally enabling workflow_run or dispatch.

    The final targeted cleanup found no necessary internal caller or documented compatibility requirement for the disabled rAthena placeholder. The exit-only script and its execution test were removed. The old unsafe installer remains disabled without replacement; no alternative unsafe installation was enabled. Unknown external callers now receive a missing-file error instead of exit guidance. Both renamed-file references were checked in tracked and untracked public files. Before documentation edits the existing tracked diff matched its starting hash; only additive test/documentation edits were made, with no reset, staging or commit.
